# 프롬프트 3기법 비교 리포트

## 1. 과업 정의
- **선택**: (나) 리뷰 분류
- **분류 항목**: `[배송, 품질, 가격, 서비스, 기타]`
- **긴급도 기준 (1~3점)**:
  - **1점 (낮음)**: 단순 칭찬, 제품 만족, 시간 민감성이 없는 일반 후기
  - **2점 (보통)**: 일반적인 성능/디자인 불만, 단순 문의 및 개선 요청
  - **3점 (높음/긴급)**: 파손/오배송, 제품 기능 마비, 응대 지연으로 인한 환불 및 빠른 조치 요구
- **출력 형식**: `{"type": "카테고리명", "urgency": 숫자}`

## 3. 프롬프트 전문

### Zero-shot
```text
다음 고객 리뷰를 분석하여 카테고리[배송, 품질, 가격, 서비스, 기타] 중 하나로 분류하고, 대응 긴급도(1~3)를 판정하세요.

[긴급도 판정 기준]
- 1점: 단순 칭찬, 제품 만족, 시간 민감성 없는 후기
- 2점: 일반적인 성능/디자인 불만, 단순 문의 및 개선 요청
- 3점: 파손/오배송, 기능 마비, 응대 지연으로 인한 빠른 환불/조치 요구

다른 설명이나 인사말 없이 오직 아래 JSON 형식으로만 답변하세요.
{"type": "분류카테고리", "urgency": 긴급도숫자}

리뷰: "[테스트 문장 입력]"

### Few-shot
```text
다음 고객 리뷰를 분석하여 카테고리[배송, 품질, 가격, 서비스, 기타] 중 하나로 분류하고, 대응 긴급도(1~3)를 판정하세요.

[긴급도 판정 기준]
- 1점: 단순 칭찬, 제품 만족, 시간 민감성 없는 후기
- 2점: 일반적인 성능/디자인 불만, 단순 문의 및 개선 요청
- 3점: 파손/오배송, 기능 마비, 응대 지연으로 인한 빠른 환불/조치 요구

다른 설명 없이 오직 JSON 형식으로만 답변하세요.

[예시 1]
리뷰: "제품에 기스가 심하게 난 채로 배송되었어요. 교환해주세요."
{"type": "품질", "urgency": 3}

[예시 2]
리뷰: "배송 추적 조회가 계속 안 되는데 언제쯤 도착하나요?"
{"type": "배송", "urgency": 2}

[예시 3]
리뷰: "디자인이 예쁘고 마감이 깔끔해서 마음에 듭니다."
{"type": "품질", "urgency": 1}

[실제 분석할 리뷰]
리뷰: "[테스트 문장 입력]"

### CoT
```text
다음 고객 리뷰를 순서대로 분석하세요.

[긴급도 판정 기준]
- 1점: 단순 칭찬, 제품 만족, 시간 민감성 없는 후기
- 2점: 일반적인 성능/디자인 불만, 단순 문의 및 개선 요청
- 3점: 파손/오배송, 기능 마비, 응대 지연으로 인한 빠른 환불/조치 요구

1단계: 고객이 언급한 핵심 문제와 감정 상태를 분석하세요.
2단계: 대응 긴급도(1~3)를 판단한 이유를 설명하세요.
3단계: 분석을 바탕으로 마지막 줄에는 오직 아래 JSON 형식만 단독으로 출력하세요. (마지막 줄에는 JSON 외에 어떠한 텍스트도 포함해서는 안 됩니다.)

{"type": "분류카테고리", "urgency": 긴급도숫자}

리뷰: "[테스트 문장 입력]"

## 4. 결과 표 (15회)

#,Zero-shot 결과 | Few-shot 결과 | CoT 결과
1. Zero-shot | "{""type"": ""품질"", ""urgency"": 1}(형식 O / 정답 O)" | Few-shot: {""type"": ""품질"", ""urgency"": 1}(형식 O / 정답 O)" | CoT: "1~2단계 추론 포함{""type"": ""품질"", ""urgency"": 1}(형식 O* / 정답 O)"

2. Zero-shot: "{""type"": ""배송"", ""urgency"": 3}(형식 O / 정답 O)" | Few-shot: "{""type"": ""배송"", ""urgency"": 3}(형식 O / 정답 O)" | CoT: "1~2단계 추론 포함{""type"": ""배송"", ""urgency"": 3}(형식 O* / 정답 O)"

3.Zero-shot: "{""type"": ""서비스"", ""urgency"": 2}(형식 O / 정답 O)" | Few-shot: "{""type"": ""서비스"", ""urgency"": 2}(형식 O / 정답 O)" | CoT: "1~2단계 추론 포함{""type"": ""서비스"", ""urgency"": 2}(형식 O* / 정답 O)"

4.Zero-shot: "{""type"": ""배송"", ""urgency"": 3}(형식 O / 불일치판정)" | Few-shot: "{""type"": ""배송"", ""urgency"": 3}(형식 O / 불일치판정)" | CoT: "1~2단계 추론 포함{""type"": ""배송"", ""urgency"": 3}(형식 O* / 불일치판정)"

5.Zero-shot: "{""type"": ""품질"", ""urgency"": 2}(형식 O / 정답 O)" | Few-shot: "{""type"": ""품질"", ""urgency"": 2}(형식 O / 정답 O)" | CoT: "1~2단계 추론 포함{""type"": ""품질"", ""urgency"": 2}(형식 O* / 정답 O)"

*CoT 형식 준수(O) 판정 기준: 프로그램이 약속한 '마지막 줄만 꺼내어' json.loads()로 정상 읽기 성공한 경우 O로 판정.

## 5. 반복 실행 (애매 사례 #4 , 기법별 3회)

기법 | 1회 | 2회 | 3회 | 같은 답이었나 
Zero-shot | "{""type"": ""배송"", ""urgency"": 3}" | "{""type"": ""배송"", ""urgency"": 3}" | "{""type"": ""배송"", ""urgency"": 3}" | O (일치) — 3회 연속 동일하게 배송으로 분류
Few-shot | "{""type"": ""배송"", ""urgency"": 3}" | "{""type"": ""배송"", ""urgency"": 3}" | "{""type"": ""배송"", ""urgency"": 3}" | O (일치) — 3회 연속 동일하게 배송으로 분류
CoT | "추론 + {""type"": ""배송"", ""urgency"": 3}" | "추론 + {""type"": ""배송"", ""urgency"": 3}" | "추론 + {""type"": ""배송"", ""urgency"": 3}" | O (일치) — 3회 연속 동일 논리 및 배송 분류

## 6. 분석
형식 준수:

Zero-shot과 Few-shot은 추가 설명 없이 순수 JSON 문자열만 출력하여 백엔드 파이프라인에서 json.loads() 파싱이 즉시 성공했습니다.

CoT는 1단계와 2단계의 한글 추론 문장이 상단에 함께 생성되었지만, 사전 약속된 백엔드 규칙("마지막 줄만 슬라이싱하여 읽는다")을 적용했을 때 예외 없이 정확한 JSON 데이터를 파싱할 수 있었습니다.

분류 정확성 및 경계 사례 분석:

명확한 사례(#1~#3)에서는 세 기법 모두 100% 일치하는 정답을 출력했습니다.

경계가 애매한 사례인 #4문장("배송 지연 -> 환불 요청")은 '배송'과 '서비스' 두 가지 영역에 걸쳐 있으며(배송 | 서비스), LLM은 3가지 기법 모두 고객의 최종 요청(환불)보다 문제의 근본 원인인 '배송 지연'을 우선시하여 '배송'으로 수렴했습니다.

#5문장("할인 만족 + 소음 불만") 역시 '가격'과 '품질' 두 속성이 대립하였으나(가격 | 품질), LLM은 긍정적 측면(할인)보다 부정적 사용성 문제(소음)를 더 중요하게 여겨 세 기법 모두 '품질'로 정확히 분류했습니다.

일관성:

#4번 문장을 기법별로 추가 2회(총 3회) 반복 실행한 결과, 3가지 기법 모두 100% 동일한 결과({"type": "배송", "urgency": 3})를 유지하여 높은 일관성을 보여주었습니다.

비용 (토큰 사용량):

Zero-shot과 Few-shot은 필요한 JSON 코드만 출력하므로 출력 토큰 수가 적어 비용 및 응답 속도 측면에서 효율적입니다.

CoT는 2줄 내외의 한글 추론 과정이 포함되어 출력 토큰량이 늘어나며, 이에 따른 API 호출 비용 증가 및 응답 지연(Latency) 요소가 발생합니다.

## 7. 결론 - 우리 팀이 쓸 기본 전략

기본 프롬프트 전략으로 Few-shot Prompting을 채택합니다.

선택 이유:

안정적인 형식 구조 및 일관성: Zero-shot 대비 예시(Example)를 통해 출력 형식을 강력하게 고정하므로 파싱 에러 방지에 가장 유리합니다.

시스템 연동 및 토큰 비용 최적화: CoT 역시 높은 분류 안정성을 보였지만 매번 불필요한 추론 텍스트가 함께 생성되어 토큰 비용이 늘어나고 전처리 로직이 요구됩니다. 반면 Few-shot은 순수 JSON 단독 출력이 보장되어 백엔드 서비스 연동에 최적화되어 있습니다.

시스템 적용 규칙:

애매한 문의/리뷰 항목 처리 시 LLM이 '근본 원인' 위주로 판단함을 고려하여, CS 분류 강화를 위한 Few-shot 예시 보완을 진행합니다.

백엔드 코드 연동 시 파싱 예외에 대응하는 try-except 구문 및 재시도(Retry) 로직을 필수로 탑재합니다.
